# АДС / Work Orders

Дата актуализации: 2026-04-07

## 1. Назначение подсистемы

Подсистема АДС отвечает за:

- регистрацию и жизненный цикл заявок;
- маршрутизацию заявки в подразделение компании;
- назначение ответственного исполнителя;
- контроль SLA;
- фиксацию истории статусов и событий;
- прикрепление фото результата.

Центральная сущность: `request_mgmt.work_order`.

## 2. Что реально работает сейчас

Проверено по коду и БД:

- основные модели и таблицы живут в приложении `work_orders`;
- карточка заявки и API действий работают через `work_orders/views.py`;
- статусы хранятся в `request_mgmt.work_order_status_ref`;
- история статусов хранится в `request_mgmt.work_order_status_history`;
- правила переходов хранятся в `request_mgmt.work_order_status_transition`;
- SLA-нормативы хранятся в `request_mgmt.sla_policy`;
- экземпляры SLA хранятся в `request_mgmt.sla_instance`;
- фото результата хранятся в `request_mgmt.work_order_attachment`.

Старый исполнительский слой через `public.bot_service_requests` признан legacy и выведен из маршрутизации. Удаление legacy-таблиц и старых URL фиксируется отдельной миграцией `work_orders/migrations/0012_refactor_ads_status_flow_and_drop_legacy_executor.py`.

## 4. Текущая проблема архитектуры

До текущего шага код и модель расходились:

- в шаблоне карточки использовались удаленные поля (`current_external_status`, `completed_at`);
- `sla_policy` и `sla_instance` существовали, но не были встроены в реальный цикл исполнения;
- `work_order_attachment` существовала, но UI привязки фото результата не был встроен в рабочий процесс;
- старые маршруты `/executor/take/...`, `/executor/report/...` и т.д. продолжали жить отдельно от `work_order`.

## 5. Целевая статусная модель АДС

Зафиксированный целевой поток:

1. `new_registered` / `Новая`
2. `accepted_by_executor` / `Назначен ответственный`
3. `in_progress` / `В работе`
4. `localized` / `Локализовано`
5. `completed` / `Выполнена`
6. `closed` / `Закрыта`

Важное правило:

- руками выбирать статус можно только Django-superuser в админке;
- рабочий UI должен двигать заявку только штатными кнопками следующего шага.

## 6. Целевые действия пользователя

Новая:

- кнопка `Установить ответственного`;
- действие назначает исполнителя и переводит заявку в статус `Назначен ответственный`.

Назначен ответственный:

- кнопка `Взять в работу`;
- переводит в `В работе`.

В работе:

- кнопка `Локализовать`;
- требует заполненного `resolution_text`;
- при отсутствии фото результата задает подтверждение.

Локализовано:

- кнопка `Выполнить`;
- требует заполненного `resolution_text`;
- при отсутствии фото результата задает подтверждение.

Выполнена:

- кнопка `Закрыть`;
- активна только для ролей `chief_engineer`, `direktor_uk` и Django-superuser.

## 7. Как сейчас реализован SLA

### 7.1. `SLA-политики`

Таблица: `request_mgmt.sla_policy`.

Это норматив:

- для конкретной компании;
- для конкретной услуги;
- для приоритета;
- отдельно для аварийного и неаварийного сценария.

Ключевые поля:

- `company_id`
- `service_id`
- `priority_code`
- `is_emergency`
- `work_start_minutes`
- `localization_minutes`
- `resolution_minutes`
- `calendar_type`
- `policy_source`

На 2026-04-07 после унификации SLA в БД действует единый базовый профиль:

- `SLA реакции` = `5` минут;
- `SLA локализации` = `120` минут;
- `SLA выполнения` = `300` минут;
- календарь = `24x7`;
- источник политики = `company`.

Политики были полностью пересозданы по матрице:

- `6 компаний`;
- `44 услуги`;
- `4 приоритета`;
- `2 режима` (`is_emergency = false/true`).

Итог: создано `2112` записей `sla_policy`.

После этого для текущих боевых заявок автоматически создались `sla_instance`.

### 7.2. `SLA экземпляры`

Таблица: `request_mgmt.sla_instance`.

Это рассчитанный SLA для конкретной заявки.

Экземпляр хранит:

- дедлайн;
- момент остановки счетчика;
- итоговое состояние (`waiting`, `met`, `overdue`, `not_applicable`).

Исторически модель предусматривала больше таймеров, чем реально нужно в АДС:

- `executor_assignment_*`
- `work_start_*`
- `resident_contact_*`
- `localization_*`
- `resolution_*`
- `auto_close_*`

Для целевой АДС-модели используются три ключевых линии:

- `work_start_*` = `SLA реакции`
- `localization_*` = `SLA локализации`
- `resolution_*` = `SLA выполнения`

`executor_assignment_*` и `resident_contact_*` считаются архитектурным резервом/наследием прошлой концепции и в текущем UI не являются первичными.

## 8. Целевая SLA-логика

### SLA реакции

- считается от `work_order.created_at`;
- останавливается при первом переходе заявки в `in_progress`.

### SLA локализации

- считается от `work_order.created_at`;
- останавливается при первом переходе в `localized` или `completed`.

### SLA выполнения

- считается от `work_order.created_at`;
- останавливается при переходе в `completed`.

### Отображение в карточке

В верхней части карточки должны идти 3 строки SLA:

- `SLA реакции`
- `SLA локализации`
- `SLA выполнения`

Пока SLA не остановлен:

- показывается обратный отсчет;
- если дедлайн уже прошел, показывается просрочка.

После остановки:

- если заявка уложилась в норматив: зеленая строка `Успех!`;
- если нет: красная строка `просрочен на ...`.

## 9. Как компании должны задавать свои SLA

Правильная модель уже поддерживается таблицей `request_mgmt.sla_policy`:

- каталог услуг общий;
- компания сама создает свои нормативы по нужным услугам;
- норматив задается в разрезе:
  - `company`
  - `service`
  - `priority`
  - `is_emergency`

То есть один и тот же сервис из общего каталога может иметь разные SLA у разных компаний.

Практический вывод:

- проблема отсутствия SLA-политик для части компаний снята;
- теперь любая новая заявка получает SLA автоматически при наличии валидной пары `company + service + priority + is_emergency`.

## 10. Что изменено в коде на этом шаге

- карточка заявки перестроена под пошаговый статусный поток;
- добавлен статус `localized` через миграцию;
- статус `accepted_by_executor` переименован в пользовательское имя `Назначен ответственный`;
- SLA в карточке считается через `sla_policy` -> `sla_instance`;
- добавлена загрузка фото результата в `work_order_attachment`;
- при переходах `В работе -> Локализовано` и `Локализовано -> Выполнена` без фото появляется подтверждение;
- закрытие ограничено ролями руководства/суперпользователя;
- legacy-маршруты старого executor-контура выведены из `portal/urls.py`;
- raw SQL-функции старого executor-контура удалены из `portal/views.py`;
- legacy-шаблон `portal/templates/portal/executor_dashboard.html` удален из runtime.
- единый базовый SLA развернут на все компании и услуги каталога;
- для текущих боевых заявок созданы `sla_instance`.

## 11. Что еще остается на следующий этап

- добавить нормальный просмотр/скачивание прикрепленных фото результата;
- развести новые и резервные SLA-поля по архитектурным ролям;
- при необходимости вынести workflow из views в полноценный service layer.

Ограничение ретро-данных:

- у существующих заявок `131`, `132`, `133` исторические записи в `work_order_status_history` отсутствуют;
- поэтому SLA-таймеры для них создаются и считаются, но остановка по прошлым переходам не может быть восстановлена задним числом без отдельного backfill-правила;
- для новых заявок и новых штатных переходов SLA работает на текущем workflow, потому что история статусов теперь записывается в коде.

## 12. Обновление 2026-04-09

### Нумератор заявок

С 2026-04-09 в `request_mgmt.work_order` действует новый стандартный нумератор:

- формат номера: `{company_id}-{company_sequence_no}`;
- `company_id` сейчас используется как код компании, потому что отдельного поля `company_code` в модели `nsi.Company` нет;
- `company_sequence_no` — сквозной порядковый номер внутри компании;
- нумератор назначается автоматически при создании новой заявки в `WorkOrder.save()`;
- существующие заявки перенумерованы по правилу `ORDER BY created_at, id` внутри каждой компании.

Примеры после перенумерации:

- заявка `id=131` -> `3-5`;
- заявка `id=132` -> `3-6`;
- заявка `id=133` -> `4-1`.

Контрольные тестовые заявки для проверки живого SLA в админке:

- `3-7` (`id=135`);
- `4-2` (`id=136`).

Обе заявки созданы 2026-04-09 как `is_test=True` и на момент проверки имели состояния SLA: `waiting / waiting / waiting`.

### Упрощение SLA-модели

С 2026-04-09 из рабочей SLA-модели удалены лишние разрезы:

- удалены из БД и интерфейса `is_emergency` на уровне `sla_policy`;
- удалены из БД и интерфейса `executor_assignment_minutes` / `Срок назначения исполнителя (мин)`;
- удалены из БД и интерфейса `work_start_minutes` / `Срок взятия в работу (мин)` как старое имя;
- удалены из БД и интерфейса `resident_contact_minutes` / `Срок контакта с заявителем (мин)`;
- удалены из БД и интерфейса `auto_close_after_days` / `Автозакрытие через (дни)`.

Вместо этого зафиксирована трехлинейная модель SLA:

- `reaction_minutes` = `SLA реакции`;
- `localization_minutes` = `SLA локализации`;
- `completion_minutes` = `SLA выполнения`.

Экземпляр SLA (`request_mgmt.sla_instance`) тоже приведен к трем таймерам:

- `reaction_*`;
- `localization_*`;
- `completion_*`.

Удалены legacy-поля экземпляра SLA:

- `executor_assignment_*`;
- `resident_contact_*`;
- `auto_close_*`.

### Что такое `policy_source`

Поле `policy_source` оставлено в модели `request_mgmt.sla_policy` как служебный источник происхождения норматива.

Факты:

- тип поля: `CharField`;
- справочник значений (`choices`): `normative`, `company`, `mixed`;
- пользовательские подписи: `Нормативный`, `Внутренний компании`, `Смешанный`;
- на текущий алгоритм выбора SLA это поле не влияет.

Текущий алгоритм `resolve_sla_policy()` выбирает политику только по:

- `company`;
- `service`;
- `priority_code`;
- `is_active`.

То есть `policy_source` сейчас является метаданными для архитектуры и будущего развития, а не управляющим фактором workflow.

### Дополнение по `policy_source`

На 2026-04-09 поле `policy_source` удалено из рабочей модели `sla_policy`.

Причина:

- поле не участвовало в алгоритме выбора SLA;
