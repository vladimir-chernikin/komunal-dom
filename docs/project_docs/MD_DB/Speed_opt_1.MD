## Что реально тормозит

1. Главный источник задержки - последовательные LLM-вызовы GigaChat. На тяжелых шагах почти всё время уходит туда.
2. После того как адрес уже найден и locked, каждый следующий обычный текст всё равно запускает `address_agent.update_optional_slots`. Это один LLM-вызов `AddressAgent.slots`, обычно 300-520 ms.
3. На шаге контакта система делает сразу три LLM-вызова: guard, проверка адресных слотов, контактные слоты. Поэтому простой контакт занял около 1.2 s.
4. На описании проблемы добавляются еще `ProblemAgent.fragment` и `ServiceSelectionAgent`. Поэтому один короткий текст "течет труба" занял больше 3.2 s.
5. `service_selection` каждый раз заново считает service type, category и localization. На уточнении места уже были понятны service type и category, но они пересчитались снова. Это лишние примерно 900 ms.
6. `decision_guard` добавил еще около 528 ms на шаге, где справочник уже дал услугу.
7. Подтверждение `да` сначала прошло через `dialog_guard.check`. Это лишние примерно 230-314 ms перед созданием заявки.
8. PostgreSQL сейчас не главный тормоз:
   - `catalog.get_snapshot`: 3.9 ms холодный старт, 0.0 ms из кеша;
   - prompt templates: около 0.8-1.2 ms каждый;
   - `resolve_service`: 1.5 ms;
   - запись/обновление `dialog_logs`: обычно 1-25 ms.

## План оптимизации `ingress_normalize`

### 1. Финальная проверка вместо `service_confirmation`

Старая стадия `service_confirmation` удаляется из рабочей логики. Сохраненные `state_snapshot` в `dialog_logs`, где stage был `service_confirmation`, мигрированы на `pre_registration_review`.

Теперь ответ пользователя на финальную проверку разбирает `FinalReviewAgent`, а не hard-code да/нет. Это нужно, чтобы фразы вроде "да, только квартира 12" или "нет, телефон другой" не приводили к неверной регистрации.

Планируемый профит: устранение зацикливания и неправильного подтверждения.

### 2. Не запускать тяжелый address update, если адрес locked и текст явно не адрес

Идея: перед `address_agent.update_optional_slots` сделать дешевую проверку на адресные признаки: `город`, `ул`, `улица`, `дом`, `кв`, цифры рядом с адресными словами, известная улица/дом. Если признаков нет, пропускать LLM-слоты адреса.

Планируемый профит: 300-520 ms на большинстве сообщений после найденного адреса.

Риск: пользователь может исправить адрес свободной фразой без явных слов. Поэтому на стадиях уточнения адреса старую ветку сохранять, а после locked разрешить полный address update только при адресных признаках.

### 3. Контакты: сначала дешевые правила, потом LLM

Идея: телефон почти всегда можно вытащить регуляркой. Имя часто идет рядом с телефоном короткой фразой. Если правило уверенно нашло имя и телефон, LLM `ContactAgent.slots` не нужен.

Планируемый профит: 300-400 ms на шаге контакта.

Риск: имя можно неправильно распознать. Нужны строгие правила и fallback на текущий LLM, если уверенности нет.

### 4. Не запускать `_record_problem_fragment` для очевидно не проблемных сообщений

Идея: не отправлять в `ProblemAgent.fragment` чистые контакты, чистые адреса, чистые `да/нет`, пустые приветствия. Сейчас часть такого уже есть, но можно расширить легкими правилами.

Планируемый профит: 300-360 ms на сообщениях, где проблема точно не добавляется.

Риск: нельзя выкинуть короткое уточнение вроде "в ванной" или "в подъезде", потому что это полезная часть проблемы. Для таких фраз старую обработку оставить.

### 5. Не пересобирать problem/context дороже необходимого

Идея: хранить подпись списка fragments и пересобирать `txtPrb` только если fragments реально изменились.

Планируемый профит: небольшой, обычно меньше 5 ms. Это не главный приоритет.

Риск: низкий, если подпись считается по фактическим fragments.

## План оптимизации `service_selection`

### 1. Не пересчитывать уверенные фильтры при малом изменении `txtPrb`

Идея: хранить в state хеш `classification_text`, `catalog_version` и уверенные значения service type/category/localization. Если пользователь добавил только место ("в ванной"), не пересчитывать service type и category.

Планируемый профит: около 800-950 ms на уточнении места.

Риск: если новый текст меняет смысл проблемы, старую классификацию использовать нельзя. Нужна проверка "существенно изменился ли txtPrb".

### 2. Параллелить независимые LLM-классификаторы

Идея: `service_type`, `category`, `localization` не зависят друг от друга и могут выполняться через `asyncio.gather`. Потом уже запускать `decision_guard`, если он нужен.

Планируемый профит: `service_selection` может упасть примерно с 1.9 s до 0.9-1.1 s.

Риск: GigaChat может отклонить параллельные запросы по лимиту. Тест 2026-05-09 показал 429 на 2-3 параллельных запросах, поэтому эта оптимизация перенесена на Stage 3.

### 3. Не запускать `decision_guard`, когда справочник дал единственный сервис и уверенность высокая

Идея: если комбинация service type + category + localization дает ровно одну активную услугу, confidence у всех фильтров высокий, а category/localization не конфликтуют, можно пропустить guard.

Планируемый профит: около 500-530 ms.

Риск: guard сейчас ловит неверную пару category/localization. Пропускать его можно только на очень уверенных случаях, плюс оставить флаг для быстрого отката.

### 4. Кешировать prompt templates

Идея: держать активные templates в process-level кеше с TTL или версией `updated_at`.

Планируемый профит: маленький, около 1 ms на prompt. Это не главный тормоз, но уменьшит SQL-шум.

Риск: после правки prompt в админке кеш может жить до TTL. Нужен короткий TTL или версия.

### 5. Catalog snapshot уже кешируется

Сейчас `CatalogProvider` уже имеет TTL 60 секунд. Baseline показал: 3.9 ms на холодном чтении и 0.0 ms на прогретом. Это не узкое место.

### 6. Уменьшить category prompt или сделать shortlist

Идея: `ServiceSelectionAgent.category` получает prompt около 6600 символов и тратит около 490-500 ms. Можно сначала дешево выбрать 3-5 вероятных категорий, а не отправлять весь справочник.

Планируемый профит: примерно 100-250 ms на category.

Риск: если shortlist ошибется, правильная категория не попадет в prompt. Нужен fallback на полный справочник при низкой уверенности.

### 7. Правила для очевидных service type/localization

Идея: "течет", "сломалось", "не работает" почти всегда `Инцидент`; "в квартире" почти всегда `Индивидуальное`, "в подъезде" - `Общедомовое`.

Планируемый профит: 400-500 ms за каждый пропущенный LLM-фильтр.

Риск: правила не должны менять смысл диалога. В сомнительных случаях оставлять LLM.

### 8. Вопросы-уточнения для типовых случаев без LLM

Идея: для частых missing_fact вроде "нужно место проявления" использовать готовый вопрос, а не два LLM-вызова generator+validator.

Планируемый профит: около 590 ms на уточняющем вопросе.

Риск: это уже меняет текст ответа. По условию Stage 1 нельзя, на Stage 2 нужно отдельно согласовать.

## Безопасность кешей

- Глобально можно кешировать только справочники и prompt templates, потому что они одинаковые для всех пользователей.
- Нельзя глобально кешировать state, контакты, адреса, `txtPrb`, выбранные услуги и решения LLM без ключа сессии.
- Кеш классификации должен лежать в state конкретной сессии и иметь ключ: `classification_text_hash + catalog_version + company_id`.
- OAuth-токен GigaChat можно кешировать как сейчас, но нельзя писать его в dialog metadata, логи или performance result.

## PostgreSQL: что проверить, но не первым делом

Сейчас SQL не выглядит главным источником задержки. Если после LLM-оптимизаций SQL станет заметен, проверить `EXPLAIN ANALYZE` и индексы:

- `llm_tester_prompttemplate(slug, is_active, id DESC)`;
- `services_catalog(is_active, type_id, localization_id, category_id)`;
- `company_service_route(company_id, service_id, is_active)`;
- `dialog_logs(session_id, timestamp)` или `dialog_logs(session_id, id)` для истории сессии;
- адресные индексы по `street_fias_guid`, `house_number`, `fias_guid` уже частично есть в моделях/migrations.

## Дополнение: тест параллельных запросов GigaChat

Дата: 2026-05-09.

Проверка выполнялась прямыми параллельными запросами к `/chat/completions` с очень коротким prompt и `max_tokens=30`.

Результат:

- 2 параллельных запроса: 1 ответ `200`, 1 ответ `429 Too Many Requests`.
- 3 параллельных запроса: 1 ответ `200`, 2 ответа `429 Too Many Requests`.

Вывод: текущий `client_id` работает как один одновременный поток. Поэтому простое `asyncio.gather()` внутри `service_selection` сейчас даст ошибки 429, а не ускорение.

Практический план:

1. До изменения тарифа/лимитов не включать параллельные LLM-вызовы в production.
2. В коде можно заранее предусмотреть feature flag и semaphore: `GIGACHAT_MAX_PARALLEL_REQUESTS=1` сейчас, `2-3` после расширения лимитов.
3. Для ускорения на текущем лимите сначала делать skip/cache/fast path, а не параллелизм.
4. Если нужен параллелизм, перевести доступ на юрлицо/ИП или запросить увеличение потоков у поддержки GigaChat.

## Уточнение после обсуждения: новая логика финальной проверки

Старая логика `service_confirmation` с простым вопросом "можно оформлять?" считается неверной. Нужен не жесткий yes/no-шлюз, а финальная проверка заявки.

Новая цель:

1. После выбора услуги бот не регистрирует заявку сразу.
2. Бот показывает человеку краткую проверку:
   - адрес;
   - описание проблемы;
   - контактное лицо;
   - способ связи;
   - подсказку "например, квартиру", если квартира не указана.
3. Ответ на эту проверку должен обрабатывать главный оркестратор после safety guard.
4. Если пользователь добавляет/исправляет адрес, контакт или проблему, оркестратор обновляет соответствующую часть state.
5. Если пользователь говорит, что добавлять нечего и можно регистрировать, заявка создается.
6. После создания заявки:
   - Telegram/MAX получают текстовый маркер `<-------- Диалог завершен --------->`;
   - WebChat получает `close_session=true` и начинает новый `session_id`;
   - API получает `close_session=true`, чтобы Asterisk мог завершить звонок.

Эта часть уже внесена до Stage 2 как исправление логики.

## Уточнение API телефонии

Для `/chat/api/external/` принят новый контракт `asterisk_voice_v2`.

Входящий JSON:

```json
{
  "schema_version": "asterisk_voice_v2",
  "source": "asterisk",
  "channel": "voice",
  "token": "string",
  "session_id": "string",
  "user_id": "string",
  "message": "string",
  "call": {
    "direction": "inbound|outbound",
    "client_phone": "string",
    "company_phone": "string",
    "asterisk_channel_id": "string"
  }
}
```

Обязательные поля:

- `schema_version`;
- `source`;
- `channel`;
- `token`;
- `session_id`;
- `user_id`;
- `message`;
- `call.direction`;
- `call.client_phone`;
- `call.company_phone`.

Старый плоский формат больше не принимается. Верхнеуровневые поля `client_phone`, `customer_phone`, `nomer`, `НомерКлиента` не читаются endpoint-ом `/chat/api/external/`.

Телефон клиента принимается только из `asterisk_voice_v2.call.client_phone` и складывается в metadata как:

- `client_phone`;
- `api_info.client_phone`;
- `api_info.nomer`;
- `customer_identifiers.telefon`.

Данные звонка `direction`, `company_phone`, `asterisk_channel_id` складываются в `metadata.call` и `metadata.api_info`.

Ответ для `asterisk_voice_v2`:

```json
{
  "status": "success|error",
  "response": "string",
  "session_id": "string",
  "service_detected": "number|null",
  "close_session": "boolean"
}
```

`close_session=true` означает: голосовой backend сначала озвучивает `response`, затем завершает звонок.

Техническая проверка после внедрения:

- валидный `asterisk_voice_v2` запрос с `message="Привет"` вернул `status=success`, `close_session=false` и стартовый вопрос про адрес;
- запрос без обязательного `call.company_phone` вернул HTTP 400 в формате нового контракта: `status=error`, `response="Missing required field(s): call.company_phone"`, `close_session=true`.
- старый плоский payload без `schema_version="asterisk_voice_v2"` должен возвращать HTTP 400 в формате нового контракта: `status=error`, `response="Unsupported schema_version: expected asterisk_voice_v2"`, `close_session=true`.

Главный JSON состояния диалога называется `state_snapshot`. Он лежит в `dialog_logs.metadata.state_snapshot` и содержит куски адреса, контакта, проблемы, фильтры услуги, выбранную услугу и служебные поля.

## Заглушка поиска клиента

Добавлена временная функция поиска клиента. Это не production-поиск, а stub с явным комментарием для будущего code review.

Вход:

```json
{
  "id_in_system": "...",
  "id_tg": "...",
  "id_max": "...",
  "telefon": "..."
}
```

Сейчас stub возвращает клиента только для:

- телефон `+79202119023`;
- Telegram nick `v_v_ch19xx`.

Возвращаемые данные:

```json
{
  "name": "Светлейший князь Владимир",
  "contacts": {
    "id_tg": "v_v_ch19xx",
    "telefon": "+79202119023"
  },
  "addresses": []
}
```

Первичный `lookup_known_customer` запускается по разным идентификаторам:

- API/voice: `telefon` из `call.client_phone`;
- Telegram: `id_tg` / username из metadata Telegram;
- MAX: `id_max` / MAX user id из metadata MAX;
- WebChat: `id_in_system` / Django user id.

Если найдено имя, бот на шаге контакта спрашивает: `Контактное лицо это, {Имя}? Как удобно с вами связаться?`

Чего сейчас не хватает в справочнике пользователей/клиентов для production-поиска:

- отдельного клиентского профиля жителя, не смешанного с сотрудниками УК;
- полей `telegram_username` / `telegram_user_id` в профиле клиента;
- поля `max_user_id` для клиента есть в `UserProfile`, но нужен единый контракт для MAX bot metadata;
- признака подтвержденного телефона и истории телефонов;
- связи клиента с адресами/помещениями/объектами обслуживания;
- признака источника и доверия к найденному контакту: API, web auth, TG, MAX, ручная карточка.

## FinalReviewAgent: расшифровка действий

`FinalReviewAgent` возвращает одно из действий:

- `ready_to_register`: пользователь согласен, добавлять нечего; orchestrator вызывает `_create_order()`.
- `update_address`: пользователь добавил или исправил адрес, квартиру, подъезд, дом, улицу; orchestrator вызывает `address_agent.update_optional_slots()`.
- `update_contact`: пользователь исправил имя или телефон; orchestrator вызывает `contact_agent.extract()`.
- `update_problem`: пользователь добавил детали проблемы или сменил смысл обращения; orchestrator пишет фрагмент в problem и повторно запускает `service_selection`.
- `update_multiple`: в одной фразе есть несколько исправлений, например квартира и телефон; orchestrator применяет несколько блоков по `fields`.
- `clarify`: ответ непонятен; orchestrator снова показывает финальную проверку.

Кейсы orchestrator:

- адрес обновился и объект найден: state адреса и объект обслуживания обновляются;
- квартира не найдена как объект обслуживания: объект дома сохраняется, квартира добавляется в текст обращения;
- контакт стал неполным после исправления: бот возвращается к `contact_required`;
- проблема изменилась: старые фильтры услуги сбрасываются и классификация считается заново;
- все готово: создается заявка, ставится `close_session=true`.

## Prompt для Codex на стороне Asterisk

Передать в Codex, который работает в коде Asterisk-интеграции:

```text
Ты работаешь в проекте Asterisk-интеграции, которая вызывает API бота komunal-dom.ru.
Нужно изменить сценарий звонка и JSON-контракт с API.

API endpoint:
POST http://komunal-dom.ru/chat/api/external/
Content-Type: application/json

Переведи вызов API на контракт `asterisk_voice_v2`.

1. Старт диалога.

При входящем звонке или при принятом исходящем звонке сразу отправь в API стартовое сообщение:

{
  "schema_version": "asterisk_voice_v2",
  "source": "asterisk",
  "channel": "voice",
  "token": "...",
  "session_id": "...",
  "user_id": "...",
  "message": "Привет",
  "call": {
    "direction": "inbound|outbound",
    "client_phone": "...",
    "company_phone": "...",
    "asterisk_channel_id": "..."
  }
}

2. Алгоритм формирования call.

Добавь в JSON для API вызова объект call, который формируется так:

- если звонок входящий: call.direction = "inbound", call.client_phone = ВходящийНомер;
- если звонок исходящий и абонент ответил: call.direction = "outbound", call.client_phone = ИсходящийНомер;
- call.company_phone = номер компании/линии, на которую пришел входящий звонок или с которой был сделан исходящий звонок;
- call.asterisk_channel_id = технический ID канала Asterisk, если он доступен; если нет, передай пустую строку;
- номер перед отправкой нормализуй в строку телефона, сохрани плюс, если он есть;
- `schema_version`, `source`, `channel`, `token`, `session_id`, `user_id`, `message`, `call.direction`, `call.client_phone`, `call.company_phone` обязательны;
- если номер клиента пустой или технический, не вызывай API как нормальный диалог: сработай по существующей fallback-логике или переведи на оператора.

3. Голос во время ожидания API.

Пока API отвечает на первый запрос, не молчи в аудиоканале. Сразу проиграй локальную фразу:

   "Вас приветствует круглосуточная аварийно-диспетчерская служба!"

После получения ответа API проиграй через TTS текст из JSON-поля response. Не дублируй старый локальный вопрос про адрес/проблему: первый вопрос должен прийти из API.

4. Обработка ответа API.

В JSON-ответ API добавлен параметр:

{
  "status": "success",
  "response": "...",
  "service_detected": null или id,
  "session_id": "...",
  "close_session": true|false
}

Используй только close_session как основной флаг завершения разговора.

Если close_session == true:

- сначала передай полученную фразу response через TTS;
- затем заверши разговор: повесь трубку / закрой сценарий звонка;
- не отправляй следующее пользовательское сообщение в эту же session_id.

Если close_session == false:

- проиграй response через TTS;
- слушай следующий ответ абонента;
- отправь распознанный текст следующим API-вызовом с тем же `session_id`, `user_id` и объектом `call`.

5. Ошибки API.

Если API вернул status != "success", HTTP 4xx/5xx или таймаут:

- проиграй короткую аварийную фразу о временной недоступности сервиса;
- корректно заверши звонок или переведи по существующей fallback-логике, если она уже есть в проекте;
- не зацикливай повторные запросы бесконечно.
```

Примечание: во внешнем API для Asterisk должен использоваться только `close_session`. Параметр `dialog_finished` не отправляется во внешнем JSON.

### Уточненный план исправления без точечных заплаток
