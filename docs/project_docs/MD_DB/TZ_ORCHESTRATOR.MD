# ТЗ: единый оркестратор фраз и переходов диалога

Статус: отдельное ТЗ, не внедряется в рамках текущей задачи `Адрес + скорость`.

## Цель

Сделать единый слой управления диалогом, который:

- решает, какой следующий шаг нужен;
- формирует смысл вопроса;
- вызывает генератор пользовательской фразы;
- валидирует вопрос перед отправкой;
- не допускает дублирования вопросов, двух вопросов в одном сообщении и роботизированных шаблонов;
- убирает пользовательские фразы из разрозненного кода агентов.

## Проблема

Сейчас пользовательские сообщения формируются в разных местах: `BotOrderOrchestrator`, `AddressAgent`, контактные шаги, final review, guard и обработчики ошибок. Из-за этого бот звучит как набор шаблонов, а не как единый помощник.

Повторяющиеся дефекты:

- вопрос содержит две задачи сразу;
- бот заново пересказывает все данные после точечного исправления;
- шаблонный вопрос не учитывает контекст проблемы;
- ответ пользователя на один вопрос может содержать адрес, проблему и контакт, но обработчики ожидают узкий ответ;
- часть логики завязана на regex/guard/fallback вместо явного состояния диалога и LLM-генерации фразы.

## Целевая Архитектура

```text
BotOrderOrchestrator
-> DialogState
-> NextActionPlanner
-> QuestionGoal
-> QuestionGeneratorAgent
-> QuestionValidatorAgent
-> TransportAdapter
```

## State

Оркестратор работает с компактным `state_snapshot`:

- `control.stage`;
- `control.next_action`;
- `dialog_context.last_bot_question`;
- `dialog_context.last_bot_goal`;
- `address_input`;
- `problem.txtPrb`;
- `contact`;
- `review.last_decision`;
- `questions.items`.

LLM получает не весь state, а короткий срез, нужный для конкретного вопроса.

## NextActionPlanner

Планировщик возвращает JSON:

```json
{
  "action": "ask_missing_address|ask_problem|confirm_contact_name|ask_contact_method|final_review|create_order|close_dialog",
  "goal": "коротко, что надо узнать",
  "known_facts": {},
  "missing_fields": [],
  "must_not_ask": [],
  "tone": "calm"
}
```

Поля: `action` - следующий шаг; `goal` - смысл вопроса; `known_facts` - уже собранные факты; `missing_fields` - чего не хватает; `must_not_ask` - что нельзя спрашивать повторно.

## Генерация Вопроса

`QuestionGeneratorAgent` получает:

- цель вопроса;
- последний вопрос бота;
- последний ответ пользователя;
- уже собранные факты;
- запреты validator.

Правила:

- один вопрос за раз;
- без вариантов и списков, если пользователь не просил выбор;
- без технических слов `слот`, `категория`, `фильтр`, `stage`;
- если пользователь дал лишнюю полезную информацию, сначала коротко подтвердить ее, затем спросить недостающее;
- если пользователь исправил одну часть заявки, подтвердить только эту часть, не пересказывать весь review.

## Validator

Валидатор вопроса проверяет:

- вопрос ровно об одном недостающем факте;
- нет дублирования уже известного;
- нет двух вопросов в одном сообщении;
- нет технического тона;
- вопрос соответствует текущей проблеме;
- вопрос не просит квартиру там, где квартира не нужна.

Если вопрос невалиден, validator возвращает не текст пользователю, а инструкцию для повторной генерации.

## Что Остается Хардкодом

Допустимо оставить хардкодом только:

- технические ошибки уровня API/сервера;
- сообщение о создании заявки с номером;
- сообщение о запрете небезопасного запроса;
- системные флаги `close_session`, `dialog_finished`;
- короткие аварийные сообщения для телефонии при timeout или `status=error`.

Пользовательские вопросы по адресу, проблеме, контакту и review должны идти через оркестратор.

## Критерии Готовности

- все пользовательские вопросы проходят через один генератор;
- в trace видны `question_goal`, prompt генератора, raw response, validator result;
- контактный вопрос разделен на два шага: имя, затем способ связи;
- final review не повторяет весь текст после точечной правки;
- бот не спрашивает уже сообщенные детали;
- бот умеет мягко вернуть к вопросу после ругани или отвлеченной реплики.
