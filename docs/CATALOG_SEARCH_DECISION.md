# Поиск по категориям и услугам: факты и решение

## Что проверено в А

- 11 категорий имеют `llm_description`; код А действительно передаёт эти
  описания в запрос выбора категории.
- 44 активные услуги имеют поле `description`, но текущий выбор услуги его не
  читает. После выбора категории код пересекает тип, локализацию и категорию.
- чтение каталога непосредственно из PostgreSQL измерено 50 раз: медиана около
  1,1 мс, 95-й процентиль около 1,5 мс. Сама БД здесь не является причиной
  заметной задержки диалога.
- PostgreSQL на сервере поддерживает установку `pgvector`, но расширение в БД А
  не установлено.
- Redis 7 работает, но модуль Redis Search для векторного поиска не установлен.

## Вывод

Векторизация нужна не для ускорения нынешнего SQL-запроса, а для другого
качества: сопоставить свободное описание человека с близкой по смыслу
категорией/услугой. При 55 текстах отдельная «векторная БД» и приближённый
индекс избыточны. Базовый вариант — отдельная `catalog_embeddings` в той же
PostgreSQL-БД и точный поиск `pgvector`.

Вызов модели вложений — преобразования текста в числовой вектор — сам может
занять гораздо больше 1,5 мс и отдельно тарифицируется GigaChat. Поэтому его
включение в голосовой путь принимается только после измерения. Таблица входит
в проект схемы уже сейчас, чтобы не прятать будущий контракт; флаг готовности
не позволяет использовать незаполненные векторы.

## Предлагаемый поток записи каталога

1. API сохраняет категорию или услугу в PostgreSQL в одной транзакции.
2. После успешной записи увеличивается `catalog_revision`.
3. Фоновая короткая задача строит точный текст из `name`, `ai_description`,
   синонимов, исключений, типа и локализации; считает вектор и записывает его
   с моделью, размером и контрольной суммой исходного текста.
4. После готовности новой версии API одним действием заменяет снимок Redis
   `kom_dom_b:catalog:v<revision>` и публикует номер версии.
5. Рабочие процессы читают новый номер и заменяют локальный снимок целиком.
6. При недоступном Redis процесс читает PostgreSQL; это защитная сетка, а
   источником истины остаётся БД.

## Что внедрять по этапам

### Этап 1 — перенос структуры

Импортировать типы, локализации, категории и услуги. Сформировать
`source_text`, заполнить `catalog_embeddings` и опубликовать один снимок Redis.
До приёмочного измерения рабочий выбор можно сравнивать в теневом режиме:
векторный результат журналируется, но не меняет выбранную услугу.

### Этап 2 — измерение и включение

Собрать не менее 200 обезличенных пользовательских описаний с правильной
услугой. Сравнить текущий выбор, текстовый поиск и точный векторный поиск по
доле правильных первых 1/3 кандидатов, времени и стоимости. Включить результат
в бизнес-решение только при доказанном выигрыше. Размер вектора хранится в
строке и не зашивается в тип колонки до выбора модели GigaChat.

## Неприемка

- Redis становится единственным хранилищем каталога.
- внешний вызов векторизации выполняется при каждом чтении одной и той же
  категории/услуги.
- векторный поиск включён без сравнения точности и 95-го процентиля задержки.
- изменение справочника видно части процессов в старой версии, части — в новой.

## Официальные источники, проверенные 2026-07-22

- [GigaChat: выбор модели](https://developers.sber.ru/docs/ru/gigachat/guides/selecting-a-model) — `GigaChat-2` предназначена для быстрых простых задач и соответствует выбранному Lite-варианту.
- [GigaChat: создание векторных представлений](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/post-embeddings) — доступны Embeddings, Embeddings-2 и EmbeddingsGigaR, запросы тарифицируются отдельно.
- [Redis Search](https://redis.io/docs/latest/develop/ai/search-and-query/) — векторный поиск является возможностью поискового модуля, которого на текущем Redis-сервере нет.
- [pgvector](https://github.com/pgvector/pgvector) — точный поиск работает без приближённого индекса; HNSW/IVFFlat меняют скорость на полноту результата и нужны при существенно большем объёме.
