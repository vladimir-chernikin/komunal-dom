## ⚠️⚠️⚠️ 2. GITHUB - ЗОЛОТЫЕ ПРАВИЛА ⚠️⚠️⚠️

### 🔥 КРИТИЧЕСКИ ВАЖНО: Строго соблюдать workflow

**ПРАВИЛО:** ВСЯ работа ведется в feature-ветках, НИКОГДА не напрямую в main!

### ЗОЛОТЫЕ ПРАВИЛА:

1. ❌ **ЗАПРЕЩЕНО:** Работать напрямую в `main`
2. ✅ **ВСЕГДА:** Создавать отдельную branch под каждую задачу
3. ✅ **ЧАСТО:** Коммитить после каждого логического изменения
4. ✅ **ЯСНО:** Писать понятные сообщения коммитов
5. ✅ **PR:** Создавать Pull Request для слияния в main
6. ✅ **ПРОВЕРКА:** Проверять `git status` перед работой

### СТАНДАРТНЫЙ WORKFLOW:

```bash
# 1. Создаем ветку под задачу (ОДИН РАЗ)
git checkout main
git pull origin main
git checkout -b feature/краткое-описание

# 2. Работаем, ЧАСТО коммитим
git status  # ПРОВЕРКА!
git add tag_search_service.py
git commit -m "Добавить триграммный поиск"
git push

# ... работаем дальше ...
git add semantic_search_service.py
git commit -m "Исправить логику фильтров"
git push

# 3. Когда ВСЯ задача готова - создаем PR
gh pr create --title "Название задачи" --body "Описание..."

# 4. После создания PR - запросить у пользователя разрешение на слияние
#    ИЛИ подождать подтверждения
```

### КОГДА ДЕЛАТЬ КОММИТ:

✅ **СРАЗУ ПОСЛЕ каждого изменения:**
- Изменил 1-2 файла → коммит
- Исправил баг → коммит
- Добавил функцию → коммит
- Переименовал переменную → коммит

❌ **ЗАПРЕЩЕНО:**
- Оставлять изменения незакоммиченными "на потом"
- Делать несколько изменений перед коммитом
- Откладывать коммит "потом разберусь"
- Работать в main (кроме pull)

### КОГДА ДЕЛАТЬ PULL REQUEST:

✅ **Когда ВСЯ задача завершена:**
- Фича полностью реализована
- Код протестирован
- Все изменения закоммичены и запушены
- Готов к code review и слиянию

❌ **НЕ создавать PR после каждого коммита!**

### СЛИЯНИЕ PULL REQUEST:

**ПРАВИЛО:** После завершения работы над фичей:

1. Создать PR: `gh pr create`
2. Запросить у пользователя разрешение на слияние
3. Дождаться подтверждения
4. Слить PR в main: `git checkout main && git pull`
5. Удалить feature-ветку

**ПРОВЕРКА ПЕРЕД КАЖДЫМ ИЗМЕНЕНИЕМ:**
- Я в какой ветке? (`git branch`)
- Я сделал `git status`?
- Я закоммичу СРАЗУ после редактирования?
- Я создам PR только после завершения ВСЕЙ задачи?

### ОСНОВНЫЕ ПОНЯТИЯ:

| Понятие | Описание | Команда |
|---|---|---|
| **branch** | Ветка для разработки | `git checkout -b feature/xxx` |
| **main** | Главная ветка (production) | `git checkout main` |
| **commit** | Сохранение изменений | `git commit -m "msg"` |
| **push** | Отправка на GitHub | `git push` |
| **pull** | Получение изменений | `git pull` |
| **PR** | Запрос на слияние | `gh pr create` |

## txtPrb - Накопление описания проблемы

**Файл:** `/var/www/komunal-dom_ru/problem_accumulation_service.py`

**Назначение:** Итеративное накопление информации из диалога, извлечение структурированных полей, предотвращение повторяющихся вопросов.

**Принцип:** "привет" → '' (нет информации), "у меня течет" → 'у пользователя течет', "В зале" → 'у пользователя течет в зале', "Батарея" → 'у пользователя течет из батареи (отопление) в зале'

**Поля:** problem, location, source, category, severity, intensity, object

**Фильтры с confidence:** location, category, incident

**КРИТИЧЕСКИ ВАЖНО:** НЕ спрашивай то, что УЖЕ известно! Если известна локация - НЕ спрашивай "Где именно?"

**Основные компоненты:**

2. **TagSearchService** (`tag_search_service.py`) - нечеткий поиск по тегам

   - **1 кандидат:** SUCCESS → создание заявки
   - **Несколько:** AMBIGUOUS → уточнение
   - **Нет:** AMBIGUOUS → запрос уточнения

**База данных:** таблица `services` (id, name, category, object_type, incident_type, location_type, tags, keywords)
