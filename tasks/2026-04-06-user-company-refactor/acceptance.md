# Acceptance Criteria: User primary company/department refactor

## ID
2026-04-06-user-company-refactor

## A. Модель данных
1. Выбран и реализован безопасный способ хранения основной компании и основного подразделения для стандартного `django.contrib.auth.models.User`.
2. Новые primary-реквизиты доступны приложению как устойчивый источник основного business context пользователя.
3. Существующая модель `work_orders.models.UserCompanyMembership` сохранена и продолжает поддерживать множественные привязки.
4. Созданы корректные миграции схемы и миграции/шаги переноса данных.
5. Реализовано понятное правило выбора primary company/department из старых membership.

## B. Django admin пользователя
1. В `portal/admin.py` на странице пользователя в блоке `Основная информация` видны и редактируются поля:
   - `Основная компания`
   - `Основное подразделение`
2. Поля не являются только readonly text/badge-отображением старой membership.
3. Внизу той же страницы показан блок множественных привязок из `UserCompanyMembership`.
4. Блок множественных привязок относится к пользователю и позволяет видеть или редактировать связи без перехода в отдельный справочник.
5. Если возможно без поломки стека admin, `Основное подразделение` ограничено выбранной `Основной компанией`; если нет, реализована серверная валидация пары.

## C. Согласованность модели
1. Если у пользователя есть `primary_company`, то `primary_department` либо принадлежит этой компании, либо сохранение запрещается валидатором.
2. Если есть активные membership, primary-пара не противоречит активным membership.
3. Если у пользователя несколько membership, система умеет использовать их набор там, где нужен multi-company scope.

## D. Middleware и helper'ы
1. `portal/middleware.py` больше не зависит только от старой single-primary логики.
2. В request доступен основной контекст пользователя.
3. При необходимости в request или helper-функциях доступен список разрешенных company ids и department ids для multi-company сценариев.
4. `portal/mixins.py` обновлен так, чтобы фильтрация могла работать как в single-company, так и в multi-company режиме.
5. `portal/auth_views.py` не ломает вход и redirect после рефакторинга.

## E. Бизнес-логика и фильтрация
1. `work_orders/views.py` исправлен в ключевых местах, где раньше жестко выбиралась одна membership.
2. `portal/admin_views.py` использует корректный company scope пользователя.
3. Список заявок, управленческие экраны и действия исполнителя не ломаются.
4. Для single-company пользователя сохраняется простой сценарий.
5. Для multi-company пользователя фильтрация может учитывать несколько компаний и/или подразделений.

## F. UI кнопок
1. Во всех формах, использующих `templates/admin/change_form.html`, текст кнопки `Закрыть` белый.
2. Кнопка `Закрыть` остается рядом с `Сохранить`.
3. Проверка сделана на форме пользователя и минимум еще на одной форме справочника.

## G. Проверки
1. `python manage.py check` проходит успешно.
2. Форма пользователя открывается без traceback.
3. Пользователь с одной компанией сохраняется корректно.
4. Пользователь с несколькими membership сохраняется корректно.
5. Browser verification по `scenario.yaml` выполнен.
6. Сохранены `report.json` и PNG-скриншоты.

## H. Финальный отчет

3. какое правило миграции данных использовано

5. где лежит `report.json`
