# Task: Одна точка входа и одна каноническая роль пользователя

## ID
2026-04-09-single-login-single-role

## Политика интерактивности
Разрешен не более 1 вопроса за весь цикл выполнения.
Этот вопрос допустим только один раз и только если найден реальный архитектурный конфликт, который нельзя безопасно разрешить по коду.
Во всех остальных случаях:
- не спрашивай разрешение на чтение файлов
- не спрашивай разрешение на изменение уже перечисленных файлов
- не спрашивай разрешение на создание миграций
- не спрашивай разрешение на перезапуск/reload
- не спрашивай разрешение на browser verification
- не останавливайся на плане

## Что нужно получить в итоге
Нужно привести проект к понятной схеме:
- одна точка входа для всех пользователей: `/login/`
- одна каноническая роль пользователя
- эта роль редактируется на основной форме пользователя: `/admin/auth/user/<id>/change/`
- эта роль определяется именно через поле `Должность`
- дальше весь алгоритм системы строится от этой должности
- основной сценарий пользователя это:
  - одна основная компания
  - одно основное подразделение
  - одна должность
- редкий сценарий работы в нескольких компаниях остается, но выносится в отдельную вкладку `Членства в компаниях`

То есть пользователь выбирает на вкладке `Основная информация`:
- `Директор`
- `Главный инженер`
- `Исполнитель`
- `Подрядчик`
- `Житель`

и именно это поле определяет:
- куда его редиректить после входа
- какие разделы ему доступны
- какие данные он видит
- какой кабинет у него основной

## Главный архитектурный принцип
Нельзя держать три разных источника роли:
- `UserProfile.role`
- `UserProfile.job_title`
- роль в привязке пользователя к компании

Нужно оставить один источник истины.

## Целевое решение с минимальными рисками
### 1. Одна точка входа
Пользовательский вход в систему должен быть один:
- `/login/`

Правильное поведение:
- `/` либо делает redirect на `/login/`, либо остается просто страницей без формы входа
- `/admin/login/` не должен быть второй рабочей точкой входа
- если кто-то открывает `/admin/login/`, его надо переводить на `/login/` с сохранением `next=/admin/`

Итог:
- пользователь всегда логинится через одну и ту же страницу
- отдельного второго логина быть не должно

### 2. Одна каноническая роль
Каноническая роль пользователя должна определяться через `Должность`.

То есть:
- `Должность` = это и есть роль для алгоритма
- отдельный справочник роли не нужен
- отдельный второй реквизит роли не нужен

Иначе говоря:
- `Должность` перестает быть просто HR-подписью
- `Должность` становится полем, от которого зависит логика системы

### 3. Что делать с текущими полями
Минимально рискованный путь:

#### 3.1. `UserProfile.role`
- вывести из всей логики
- убрать из интерфейсов
- больше не использовать ни в login, ни в доступе, ни в redirect
- если безопасно, удалить
- если сразу удалять рискованно, оставить как legacy на один переходный этап, но код его больше не читает

#### 3.2. `UserProfile.job_title`
- сделать каноническим полем роли
- расширить/нормализовать набор значений так, чтобы они покрывали реальные роли системы
- если нужно, переименовать в коде и форме в более понятное имя, но для пользователя можно оставить подпись `Должность`

#### 3.3. роль в привязке пользователя к компании
- это поле больше не должно быть источником истины
- на переходном этапе его можно:
  - либо автоматически синхронизировать от должности
  - либо оставить как legacy-данные только для обратной совместимости
- но алгоритм не должен опираться на него как на главный источник роли

#### 3.4. `Профиль пользователя`
- отдельная вкладка `Профиль пользователя` должна исчезнуть из основного UX
- отдельная сущность не должна ощущаться как второй обязательный объект для редактирования одного и того же пользователя
- если какие-то поля пока технически остаются в `UserProfile`, они должны показываться на основной форме пользователя и не требовать от пользователя понимания отдельной сущности

## Важное ограничение
Нельзя опасно ломать весь проект попыткой одномоментно удалить все таблицы и все старые поля.

Нужен поэтапный безопасный переход:

### Этап 1
- выбрать один канонический источник роли: `Должность`
- переписать код логики на чтение только этого поля
- синхронизировать старые данные
- оставить legacy-поля только как временный хвост

### Этап 2
- убрать legacy-поля из форм
- убрать legacy-поля из кода
- при безопасности удалить их из схемы

То есть сначала нужно убрать дублирование на уровне алгоритма, а не начинать с опасного удаления таблиц.

## Что именно нужно изменить
### Блок A. Одна точка входа
Нужно исправить:
- `komunal_dom/settings.py`
- `portal/urls.py`
- `portal/views.py`
- `portal/auth_views.py`
- связанные redirect/mixins/decorators

Цель:
- `/login/` единственный пользовательский вход
- `/admin/login/` больше не воспринимается как отдельная живая login-страница
- `/` не должен создавать второй login-flow

### Блок B. Каноническая должность как роль
Нужно исправить:
- `portal/models.py`
- `portal/forms.py`
- `portal/admin.py`
- `portal/auth_views.py`
- `portal/mixins.py`
- `portal/middleware.py`
- `portal/admin_views.py`
- `portal/views.py`
- `work_orders/views.py`
- все другие места, где роль читается из старых полей

Цель:
- должность становится единственным источником роли
- все бизнес-решения строятся от должности

### Блок C. Основная форма пользователя
Главная форма:
- `/admin/auth/user/<id>/change/`

На вкладке `Основная информация` должны быть:
- username
- first_name
- last_name
- email
- is_active
- is_staff
- is_superuser
- основная компания
- основное подразделение
- должность
- телефон
- адрес
- часовой пояс

Ниже на этой же форме или в отдельной вкладке `Членства в компаниях` должен оставаться редкий дополнительный механизм множественных привязок.

Основной сценарий должен быть именно таким:
- пользователь редактируется в одном месте
- на основной форме задается основная компания
- на основной форме задается основное подразделение
- на основной форме задается должность
- именно эти поля управляют основной логикой системы

Редкий сценарий должен быть таким:
- пользователь может иметь дополнительные привязки
- каждая дополнительная привязка может содержать:
  - дополнительную компанию
  - дополнительное подразделение
  - дополнительную должность
- это настраивается отдельно на вкладке `Членства в компаниях`
- это не должно усложнять основной сценарий 1-к-1

Но:
- отдельная сущность `Профиль пользователя` не должна ощущаться как второй обязательный объект
- отдельной второй логики роли на форме быть не должно
- отдельной вкладки `Профиль пользователя` в основном UX быть не должно

### Блок D. Привязки пользователя к компаниям
Нужно упростить смысл.

Привязка к компании должна отвечать за:
- в каких компаниях работает пользователь
- в каких подразделениях работает пользователь
- какие у него есть дополнительные должности в редких случаях multi-company
- какая из привязок основная
- даты действия
- активность

Привязка к компании не должна быть вторым независимым источником роли.

Минимально безопасный вариант:
- для основной логики система берет роль из основной `Должности` пользователя
- поле роли в привязке используется только для дополнительной истории multi-company, если это реально нужно проекту
- если поле роли в привязке пока остается в таблице, нужно четко разделить:
  - основная роль системы = `Должность` на основной форме
  - дополнительная роль в членстве = локальная роль внутри редкого дополнительного кейса
- нельзя смешивать эти два смысла в коде

## Какой результат нужен в поведении системы
1. Я захожу через `/login/`
2. Если моя должность = `Директор`, система считает меня директором
3. Если моя должность = `Исполнитель`, система считает меня исполнителем
4. Если моя должность меняется на форме пользователя, алгоритм меняется тоже
5. Никаких вторых скрытых ролей и вторых справочников для роли не остается
6. В обычном сценарии мне не нужно идти в дополнительную сущность `Профиль пользователя`
7. В обычном сценарии мне не нужно идти в `Членства в компаниях`, если у пользователя одна компания
8. Вкладка `Членства в компаниях` нужна только для редкого дополнительного сценария

## Что нельзя делать
1. Нельзя оставлять дублирование:
- часть логики по `UserProfile.role`
- часть по `job_title`
- часть по membership role
2. Нельзя сделать вид, что роль одна, а на самом деле читать разные поля в разных модулях
3. Нельзя завершать задачу без миграции данных и отчета по конфликтам
4. Нельзя завершать задачу без browser verification
5. Нельзя оставлять вкладку `Профиль пользователя` как отдельный обязательный слой редактирования
6. Нельзя заставлять пользователя настраивать multi-company ради обычного сценария одной компании
