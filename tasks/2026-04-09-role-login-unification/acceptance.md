# Acceptance Criteria: Одна точка входа и одна каноническая роль

## ID
2026-04-09-single-login-single-role

## A. Вход
1. Рабочая точка входа для пользователей одна: `/login/`.
2. `/` не создает второй независимый login-flow.
3. `/admin/login/` не является второй отдельной рабочей login-страницей.
4. При открытии `/admin/login/` пользователь попадает в единый login-flow.

## B. Каноническая роль
1. Каноническая роль пользователя определяется через `Должность`.
2. `UserProfile.role` не участвует в login redirect.
3. `UserProfile.role` не участвует в доступе к кабинетам.
4. Роль из привязки пользователя к компании не является главным источником роли.
5. Для обычного сценария одной компании система берет роль с основной формы пользователя.

## C. Форма пользователя
1. На `/admin/auth/user/<id>/change/` на вкладке `Основная информация` есть поле `Должность`.
2. Именно это поле определяет роль пользователя в алгоритме.
3. Отдельной второй роли на форме нет.
4. Отдельная вкладка `Профиль пользователя` убрана из основного UX.
5. На основной форме есть `Основная компания` и `Основное подразделение`.
6. Обычный сценарий `1 пользователь = 1 компания = 1 подразделение = 1 должность` настраивается без перехода в дополнительные сущности.
7. Пользователь не обязан открывать `Членства в компаниях`, если у него только одна компания.

## D. Дополнительные привязки
1. Вкладка `Членства в компаниях` остается только для редкого дополнительного сценария.
2. В этой вкладке можно хранить дополнительные компании, подразделения и при необходимости локальную должность.
3. Наличие вкладки `Членства в компаниях` не ломает и не усложняет основной сценарий одной компании.
4. Основная роль системы не читается случайно из дополнительной привязки вместо основной `Должности`.

## E. Поведение системы
1. Пользователь с должностью директора попадает в директорский кабинет.
2. Пользователь с должностью исполнителя попадает в исполнительский кабинет.
3. Пользователь без привязки к компании обрабатывается предсказуемо.
4. После смены должности на форме пользователя алгоритм реально меняется.
5. Пользователь с несколькими компаниями обрабатывается корректно, но это остается отдельным дополнительным сценарием.

## F. Legacy-поля
1. Если `UserProfile.role` не удален физически, он больше не управляет алгоритмом.
2. Если поле роли в membership не удалено физически, оно больше не является главным источником роли.
3. Есть отчет по синхронизации legacy-полей.
4. Если `UserProfile` физически еще существует, он не торчит отдельной вкладкой и не заставляет пользователя редактировать вторую сущность.

## G. Проверки
1. `python manage.py check` проходит без ошибок.
2. Ключевые страницы не содержат `FieldError`, `Traceback`, `500`.
3. Выполнена браузерная проверка.
4. Есть скриншоты и JSON-отчет.
